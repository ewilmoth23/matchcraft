# Development

## Setup

Use Python 3.12 and Node.js 22 or newer:

```bash
cp .env.example .env
make install
make migrate
```

`make install` creates a root `.venv`, installs `apps/api` in editable mode with development extras, and runs `npm ci` in `apps/web`.
Python resolution is constrained by `apps/api/constraints.lock`; update it deliberately with
dependency changes and verify the resolved set on macOS and Linux.

Start `make api` and `make web` in separate terminals. FastAPI reloads backend changes; Vite provides frontend hot reload.

## Migrations

```bash
make migrate
cd apps/api
../../.venv/bin/alembic revision --autogenerate -m "describe change"
../../.venv/bin/alembic upgrade head
../../.venv/bin/alembic downgrade -1
```

Review autogenerated migrations. Migrations must contain a frozen schema and must not call live
`Base.metadata.create_all()` or import application models. Test upgrades from a clean SQLite file,
downgrades where safe, and `alembic check`. Never edit an already released migration.

## Verification

```bash
make lint
make test
make build
make test-e2e
make test-e2e-full
docker compose config --quiet
```

Backend tests create isolated SQLite databases and temporary data directories. Model calls are mocked or disabled; CI needs no key, Ollama, GPU, or private documents.
The fast Playwright journey mocks API responses. The full-stack journey starts an isolated API,
applies the real Alembic migration, uses temporary SQLite storage, and exercises live persistence
and deterministic analysis through the browser. CI runs both.

## Adding a provider

1. Implement the `ModelProvider` protocol in `apps/api/app/providers`.
2. Keep provider payload parsing inside the provider layer.
3. Normalize timeouts, transport errors, invalid JSON, and provider errors as `ProviderError`.
4. Return the existing validated Pydantic output types.
5. Apply evidence and no-fabrication validation before persistence.
6. Add availability, valid response, malformed response, timeout, and unsupported-evidence tests.
7. Document exactly what data the provider receives.

Do not log prompts or raw model output.

## Modifying scoring

Scoring logic belongs in `analysis/scoring.py`. Keep weights explicit, nonnegative, and totaling 100. Add deterministic fixtures for every changed rule, update `docs/scoring-model.md`, and explain migration/version implications for saved analyses.

**Run `make eval` before and after, and put both numbers in the pull request.** A scoring
change that cannot show its effect on evidence accuracy and the fairness properties is a
guess. `make eval-gate` runs in CI and treats any fairness or soundness violation as a
failure, because those are promises the product makes in `docs/responsible-ai.md`.

Two rules learned from the harness rather than from intuition:

- A scored signal must be **evidence**, not presentation. Employment-date formatting and
  résumé word count were both removed from scoring after measurement showed the first
  penalized career breaks on 13 of 16 corpus cases and the second rewarded padding.
- A category must be **monotone** in evidence. If adding a real role can lower a
  category, the category is measuring the wrong thing.

Model judgments must be bounded and must not silently change deterministic categories.

## Sample data

`make sample` loads two synthetic analyses into the configured database. It deliberately skips AI so results remain reproducible. Never commit a real résumé or copied private job posting.

`make reset-data` shows the resolved configured data directory and requires typing `delete`. For automation, run `python scripts/reset_local_data.py --yes` only after setting and checking `MATCHCRAFT_DATA_DIR`.

## Cross-platform notes

The Makefile targets POSIX shells. On Windows, use WSL, Docker Desktop, or execute the equivalent `.venv\Scripts\...` and npm commands in PowerShell. Application paths use `pathlib`; SQLite and data locations are configurable.
